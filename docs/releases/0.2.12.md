# AgentBlazor 0.2.12 Release Notes

Target package line: `0.2.12` stable.

AgentBlazor 0.2.12 is a CLI analyzer-quality patch for real multi-project Blazor solutions.

## What Changed

- Links Razor pages that inject interfaces to the concrete implementation services discovered through DI registration and implemented interface metadata.
- Filters infrastructure, identity, storage, SignalR, generic HTTP-client, handler, validator, execution-context, and background-service plumbing from service lists, workflow suggestion prompts, and recommended next steps.
- Keeps explicitly annotated `[AgentAction]` methods visible even when the surrounding type would otherwise match an infrastructure filter.
- Accepts valid lookup suggestions where the method suffix uses generic identifiers such as `Id`, `Code`, `Key`, `Number`, or `Slug`.
- Reports `No developer-facing service-like classes were discovered.` when solution-scope analysis only finds filtered infrastructure services.

## Why

Real solution-scope runs against larger applications were no longer failing, but the reports were still too noisy. The analyzer could find too many low-level services, and the LLM would sometimes suggest workflows around storage managers, token managers, generic HTTP wrappers, validators, or import/export handlers.

This release tightens the candidate model so `agentblazor analyze --scan-scope solution` is more useful on modular and multi-project apps: app-facing services stay visible, implementation plumbing is filtered out, and hallucinated workflow suggestions are rejected instead of being shown as recommendations.

## Verification

Run:

```bash
dotnet tool update --global AgentBlazor.Cli --version 0.2.12
agentblazor analyze ./MySolution.slnx --host MyBlazorApp --scan-scope solution --output ./analysis.md
```

Expected result:

- Razor pages that inject interfaces should link to relevant implementation-service actions when method calls are visible.
- Infrastructure, identity, storage, generic HTTP-client, handler, and validator services should not appear as workflow suggestions.
- Apps with no developer-facing service candidates should say so explicitly instead of rendering an empty services section.
- Valid lookup workflows such as `GetProductBySlugAsync` should validate when the suggestion correctly references the discovered method.
