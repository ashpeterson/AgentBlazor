# Private Preview Validation

Last updated: 2026-04-18

Use this checklist when validating AgentBlazor in a real Blazor app from the private GitHub Packages feed.

## Private-Preview Limitations

- The current package targets `net10.0`; apps targeting older TFMs are outside this preview path.
- The package is private on GitHub Packages, not `nuget.org`; testers need package read access and an authenticated NuGet source.
- The primary supported auto-scaffold path is a standard `Program.cs`-based Blazor Web App server host.
- Blazor Web Apps with companion WebAssembly client projects are supported as server-host scaffold plus manual client UI review.
- Legacy, framework-owned, or highly custom hosts are review-first; the CLI should avoid unsafe startup/layout edits and report manual work.
- Provider secrets are never generated by scaffold; each app owner must configure provider keys/endpoints through their normal secret-management path.
- OpenAI is the most validated provider path for this preview. Azure OpenAI is supported through the Microsoft Azure OpenAI client and the same `IChatClient` runtime path; each Azure deployment still needs explicit app-owner validation.
- Preview validation should not be treated as production sign-off until a real app owner validates install, runtime behavior, approval UX, logging, and rollback.
- The current validated private-preview package is `0.1.0-preview.9`; GitHub Packages validation includes clean-app install, external real-app install, CSP nonce preservation, and all-surface chat browser validation against `damienbod/BlazorSecurityNet10`.

## Real-App CLI Validation Checklist

Record the repository URL, commit SHA, target project path, SDK version, CLI version, and runtime package version before changing anything. The CLI and runtime package must be the same AgentBlazor preview version because scaffolded workflow files use `AgentBlazor.App` semantic capability APIs from the runtime package.

1. Clone a fresh copy of the app and check out the validation commit.
2. Run baseline restore and build:

```bash
dotnet restore path/to/App.csproj
dotnet build path/to/App.csproj --no-restore -nologo
```

3. Add the private GitHub Packages source using a PAT with `read:packages`.
4. Install the package and CLI from the feed:

```bash
dotnet add path/to/App.csproj package AgentBlazor --version 0.1.0-preview.9
dotnet tool install AgentBlazor.Cli --version 0.1.0-preview.9 --tool-path .agentblazor-tool
.agentblazor-tool/agentblazor --version
```

For hosted WebAssembly client projects that will render browser-side remote chat surfaces, also install the matching client package:

```bash
dotnet add path/to/App.Client.csproj package AgentBlazor.Client --version 0.1.0-preview.9
```

5. Initialize and preview scaffold:

```bash
.agentblazor-tool/agentblazor init path/to/App.csproj --non-interactive
.agentblazor-tool/agentblazor scaffold path/to/App.csproj --host AppNamespace --provider openai --diff
```

6. Review the diff for host-shape safety, package references, startup wiring, shell assets, provider registration, and chat placement.
7. Apply scaffold and verify:

```bash
.agentblazor-tool/agentblazor scaffold path/to/App.csproj --host AppNamespace --provider openai --approve
dotnet restore path/to/App.csproj --force-evaluate
dotnet build path/to/App.csproj --no-restore -nologo
.agentblazor-tool/agentblazor doctor path/to/App.csproj --host AppNamespace
.agentblazor-tool/agentblazor validate path/to/App.csproj --host AppNamespace
```

8. Run a startup smoke with a non-empty placeholder provider key to catch runtime assembly/configuration failures before live-model testing:

```bash
OpenAI__ApiKey=placeholder-key dotnet run --project path/to/App.csproj --no-launch-profile --urls http://127.0.0.1:5288
curl -fsS http://127.0.0.1:5288/
```

9. Confirm the response contains AgentBlazor static assets and a chat surface. Use `--no-launch-profile` or an app-specific known URL so the probed port is the actual bound port.
10. Record all warnings separately as upstream app warnings, AgentBlazor warnings, or manual-review host-shape warnings.

## Version Mismatch Check

If the app fails after scaffold with missing `AgentBlazor.App`, `CapabilityResult`, `AgentCapability`, or `AddWorkflow`, verify that the restored package assets match the CLI version:

```bash
dotnet list path/to/App.csproj package --include-transitive
dotnet restore path/to/App.csproj --force --force-evaluate
```

Then inspect `obj/project.assets.json` and confirm `AgentBlazor.Core.dll` appears in the `compile` assets for the selected `AgentBlazor` package version. If it does not, delete the cached `agentblazor` package folder, delete `bin`/`obj`, and restore again.

## Provider Configuration Checklist

### OpenAI

- Configure `OpenAI:ApiKey` or `OpenAI__ApiKey`.
- Configure `OpenAI:Model` or `OpenAI__Model` when the default model is not appropriate.
- Use a tool-capable model for workflow/capability invocation.
- Run one startup smoke with a placeholder key, then one live workflow smoke with a real key in a controlled environment.

### Azure OpenAI

- Configure `AzureOpenAI:Endpoint`.
- Configure `AzureOpenAI:DeploymentName`.
- Configure `AzureOpenAI:ApiKey` for API-key auth, or pass an Azure `TokenCredential` such as `DefaultAzureCredential` for managed identity / Microsoft Entra auth.
- Confirm the endpoint is HTTPS and points to the Azure OpenAI resource, not the Azure Portal URL.
- Validate deployment/model compatibility with tool calling before treating the app as supported.

### Ollama

- Configure `Ollama:Model`.
- Configure `Ollama:Endpoint` when not using the default local endpoint.
- Configure `Ollama:ApiKey` only when the Ollama endpoint is protected.
- Start Ollama and pull the target model before app startup.
- Validate latency and tool-call behavior locally; Ollama is useful for private/local testing but is not the primary production-validated path yet.

## Evidence To Capture

- Package version and CLI version.
- Feed source used.
- Baseline restore/build result.
- Scaffold diff summary and manual-review notes.
- Post-scaffold restore/build result.
- `doctor` summary.
- `validate` summary.
- Runtime HTTP smoke result.
- Chat surface browser result for the installed app route and any embedded surfaces validated.
- Any live-provider workflow result, if performed.
